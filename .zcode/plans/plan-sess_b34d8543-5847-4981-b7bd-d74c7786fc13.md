## Plan: Vice-City-style third-person character (toggle with V)

**Goal:** Add a procedural blocky humanoid you can see walking around Jodhpur in third-person (Vice City style), toggled on/off with the **V** key. First-person mode (current) stays fully intact.

### Core architecture change: separate "player" from "camera"

Right now the camera *is* the player (first-person). The fix is to introduce a canonical **player state** (`playerPos`, `playerYaw`) that both modes share, and place the camera relative to it each frame:
- **First-person:** camera = playerPos + eye height, looking forward. (Exactly today's behavior.)
- **Third-person:** camera = playerPos + behind/above offset; avatar mesh drawn at playerPos.

A key correctness fix bundled in: `yaw`/`pitch` are currently stale in pointer-lock mode (PointerLockControls writes the camera quaternion directly). I'll add a single `getPlayerYaw()` helper that reads yaw from the camera's world direction — `atan2(fwd.x, -fwd.z)` (the same formula already used by the minimap at line 926). This makes the avatar's facing and the third-person camera offset correct in **both** pointer-lock and drag-to-look modes.

### Step-by-step

**1. New constants (top of file, near EYE_HEIGHT)**
- `THIRD_PERSON_DIST = 4.5` — camera distance behind avatar
- `THIRD_PERSON_HEIGHT = 2.2` — camera height above avatar feet
- `AVATAR_HEIGHT = 1.7` — for ground placement

**2. New module state (in the controls section, near `yaw`/`pitch`)**
- `let thirdPerson = false;` — current view mode
- `let avatar = null;` — the THREE.Group humanoid (created lazily on first toggle to V, so first-person stays zero-cost until then)

**3. Procedural blocky avatar builder** — `buildAvatar()` returning a `THREE.Group`:
- Torso: box ~0.5 × 0.6 × 0.3 (sandstone/orange, "Vice City" Hawaiian-shirt vibe)
- Head: box ~0.28 cube on top, skin tone
- 2 arms + 2 legs: thin boxes, stored as references (`leftArm`, `rightArm`, `leftLeg`, `rightLeg`) pivoted at the shoulder/hip so we can animate them
- Total ~50 lines, no external assets, no textures
- Origin at the avatar's feet (y=0), so placement is `avatar.position.set(playerPos.x, 0, playerPos.z)`

**4. Toggle handler** — add to the existing `keydown` listener:
- On `KeyV`: if `!avatar`, `avatar = buildAvatar(); scene.add(avatar)`. Flip `thirdPerson`. Update the overlay/HUD hint text to mention the new mode.
- Prevent the toggle key from also being read as movement (it isn't, since it's not WASD).

**5. Walk-cycle animation** — `animateAvatar(dt, moving, speed)`:
- When moving: swing arms and legs with a sine, phase advanced by `dt * speed * k`. Opposite arms/legs (left arm forward when right leg forward). Frequency scales with speed so running looks faster than walking.
- When idle: ease limbs back to neutral.
- Also rotate the avatar to face movement direction: the avatar's yaw should track `playerYaw` derived from `camera.getWorldDirection` (so it faces where you look, Vice-City-style — the character turns to face the camera's forward).

**6. Refactor the frame loop (`animate`) to use canonical player state:**

The movement/collision math (lines 857–892) currently mutates `camera.position` directly and applies head-bob to `camera.position.y`. I'll change it to:
- Compute `move` exactly as today (forward/right from `camera.getWorldDirection`, flattened).
- Apply axis-separated collision to a **`playerPos` vector** (not `camera.position` directly). `playerPos.y` stays at 0 (feet on ground) in third-person, or `EYE_HEIGHT` in first-person.
- Then position the camera based on mode:
  - **First-person:** `camera.position = playerPos + (0, EYE_HEIGHT + headBob, 0)`; head-bob stays. Camera rotation unchanged (driven by pointer-lock or `applyFallbackLook`). ← identical to today.
  - **Third-person:** camera positioned at `playerPos + behind*THIRD_PERSON_DIST + up*THIRD_PERSON_HEIGHT`, where `behind = -forwardHorizontal`. Camera looks at the avatar's upper body. Head-bob is OFF; instead `animateAvatar()` drives the limbs. The avatar mesh is positioned at `playerPos` (feet on ground) and rotated to `playerYaw`.

**7. Minimap already uses `camera.getWorldDirection`** for the heading — no change needed; it'll reflect the player's facing in both modes. The HUD coordinates use `playerPos.x/z` — trivially correct in both modes.

**8. Spawn / overlay text:** spawn stays at `(1, -24)`. Add a one-line hint to the overlay keys: "V — switch view". Update the README's controls table and add a short "Character / third-person" section.

### Risks / how I'll keep it safe
- **Don't break first-person.** The refactor is the riskiest part. I'll keep the first-person camera-placement math numerically identical to today (same EYE_HEIGHT, same head-bob amplitude/frequency), and verify in the live browser that first-person still works exactly as before toggling.
- **No external assets.** Procedural blocks only — no network dependency that can 404 or hit a license issue.
- **Verify in the IAB:** load, confirm first-person still walks, press V (simulate via the code path since the IAB swallows synthetic input — I'll add a small on-screen "press V" affordance and confirm the toggle state flips by reading a status indicator), confirm the avatar appears and the camera moves behind it, walk around to see the walk cycle, toggle back.
- **Wrap new per-frame work in try/catch** like the HUD/minimap blocks, so an avatar bug can never stall movement.

### Out of scope (won't do now)
- Animations beyond a walk cycle (no jump, no idle fidget). `GRAVITY` is already defined and unused; jumping stays for later.
- Camera collision (third-person camera clipping into a wall behind you). A real issue in tight streets; noting it as a known limitation in the README rather than solving it now.
- Driving/vehicles.
